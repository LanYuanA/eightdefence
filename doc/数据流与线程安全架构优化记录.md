## 1. 优化背景

本项目是一个 C++ 物联网网关系统，通过 Modbus RTU 协议（RS-485 串口总线）采集多种环境传感器和控制设备的数据，并通过内嵌 Web 服务器对外提供 REST API 和前端页面。

在优化前，系统存在以下架构问题：

| 序号 | 问题 | 风险等级 | 影响 |
|------|------|---------|------|
| 1 | 设备数值字段无锁保护 | **高** | 轮询线程写、Web 线程读，存在数据竞争（undefined behavior） |
| 2 | 安防应用有独立轮询线程 | **中** | 冗余数据复制，浪费 CPU，增加维护复杂度 |
| 3 | Web API 控制命令直接操作设备 | **高** | 在 Web 线程上执行 Modbus 写操作，与轮询线程竞争串口 |
| 4 | EnvDataCpp 无 getter | **低** | 加湿器和净化器的环境数据无法从外部读取 |
| 5 | Ctrl+C 无法终止程序 | **高** | 多线程信号处理不当，select() 不被中断 |
| 6 | serialBus.close() 死锁 | **高** | mutex 在 I/O 期间被持有，close() 等待 30+ 秒 |
| 7 | EnvDataCpp init() 死锁 | **高** | 非递归 mutex 二次加锁导致死锁 |

## 2. 项目整体架构

### 2.1 线程模型

系统运行时包含以下线程：

```
┌─────────────────────────────────────────────────────────────────┐
│                        进程 app_gateway                          │
│                                                                  │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐   │
│  │ 轮询线程 #1  │  │ 轮询线程 #2  │  │ 命令处理线程         │   │
│  │ (每个设备一个)│  │ (每个设备一个)│  │ (CommandQueue worker)│   │
│  └──────┬───────┘  └──────┬───────┘  └──────────┬───────────┘   │
│         │                 │                      │               │
│         └─────────────────┼──────────────────────┘               │
│                           │                                      │
│                   ┌───────▼───────┐                              │
│                   │  SerialBus    │  ← std::recursive_mutex      │
│                   │  (串口互斥锁) │                              │
│                   └───────┬───────┘                              │
│                           │                                      │
│                   ┌───────▼───────┐                              │
│                   │   RS-485 总线  │                              │
│                   └───────────────┘                              │
│                                                                  │
│  ┌──────────────┐                                                │
│  │ Web 服务器线程│  ← 处理 HTTP 请求, 读取设备数据               │
│  │ (pthread)    │                                                │
│  └──────────────┘                                                │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 数据流概览

```
  轮询线程                全局设备单例              Web 服务器
  ─────────             ─────────────             ──────────
  Modbus 读取  ──写入──→  dev_pm25.value_  ←──读取──  /api/sensors
  Modbus 读取  ──写入──→  dev_water.water_state_ ←──  /api/status
  Modbus 读取  ──写入──→  dev_humidifier.env_   ←──  /api/sensors

  命令队列线程              全局设备单例
  ────────────             ─────────────
  /api/control ──提交──→ CommandQueue ──执行──→ Modbus 写入
```

**关键数据路径：**
- **轮询线程**通过 Modbus 读取设备寄存器，解析后写入全局设备单例的字段
- **Web 服务器**直接读取全局设备单例的字段，组装 JSON 返回给前端
- **控制命令**通过 CommandQueue 异步提交，由命令处理线程串行执行 Modbus 写操作

## 3. 优化一：设备数值字段加锁保护

### 3.1 问题分析

轮询线程持续写入设备数据字段，Web 服务器线程同时读取这些字段。在 C++ 中，对非原子类型的并发读写是**未定义行为**（undefined behavior），可能导致：

- 读取到撕裂值（torn read）：例如一个 32 位写入被拆成两次 16 位写入，读线程恰好在中间读取
- 编译器优化导致缓存不一致：编译器可能将值缓存在寄存器中，不从内存重新读取
- 在 ARM 等弱内存序架构上，写入顺序可能与代码顺序不一致

### 3.2 解决方案

根据数据类型选择不同的线程安全策略：

| 数据类型 | 策略 | 原因 |
|---------|------|------|
| 简单数值（int, uint16_t） | `std::atomic` | 无锁，性能好，适合单值读写 |
| 复合结构（EnvDataCpp，含 8 个字段） | `std::mutex` | 需要保证多字段的一致性读取 |

### 3.3 简单类型：std::atomic

将所有设备的值字段从普通类型改为 `std::atomic` 类型。

**改造前（以 PM2.5 传感器为例）：**

```cpp
// dev_cloud_sensors.hpp
class DevCloudPm25 : public DeviceBase {
private:
    uint16_t value_{0};           // ← 普通类型，无保护
public:
    uint16_t getValue() { return value_; }
};
```

**改造后：**

```cpp
// dev_cloud_sensors.hpp
#include <atomic>

class DevCloudPm25 : public DeviceBase {
private:
    std::atomic<uint16_t> value_{0};  // ← 原子类型，线程安全
public:
    uint16_t getValue() const { return value_.load(); }
};
```

**对应的 cpp 文件改造：**

```cpp
// 改造前
void DevCloudPm25::procValue(const uint8_t *resp, size_t resp_len, int rc) {
    // ...
    uint16_t val = ParseService::extractU16(resp, 0);
    value_ = val;                    // ← 直接赋值，无保护
    printf("  => [📊 PM2.5]: %d\n", val);
}

// 改造后
void DevCloudPm25::procValue(const uint8_t *resp, size_t resp_len, int rc) {
    // ...
    uint16_t val = ParseService::extractU16(resp, 0);
    value_.store(val);               // ← 原子存储
    printf("  => [📊 PM2.5]: %d\n", val);
}
```

### 3.4 复合类型：EnvDataCpp 加 mutex

`EnvDataCpp` 包含 8 个环境数据字段（PM2.5、PM10、湿度、温度、TVOC、甲醛、CO2、O3）。读取方通常需要一次性获取所有字段的快照，因此需要 mutex 保证多字段的一致性。

**改造前：**

```cpp
struct EnvDataCpp {
    int pm25 = 0, pm10 = 0, humidity = 0, temperature = 0;
    int tvoc = 0, ch2o = 0, co2 = 0, o3 = 0;
    // ← 无锁保护，多线程读写不安全
};
```

**改造后：**

```cpp
struct EnvDataCpp {
    int pm25 = 0, pm10 = 0, humidity = 0, temperature = 0;
    int tvoc = 0, ch2o = 0, co2 = 0, o3 = 0;
    mutable std::mutex mtx;   // ← 互斥锁保护

    EnvDataCpp() = default;

    // 拷贝构造：锁住源对象，拷贝所有字段
    EnvDataCpp(const EnvDataCpp &other) {
        std::lock_guard<std::mutex> lock(other.mtx);
        pm25 = other.pm25; pm10 = other.pm10;
        humidity = other.humidity; temperature = other.temperature;
        tvoc = other.tvoc; ch2o = other.ch2o;
        co2 = other.co2; o3 = other.o3;
    }

    // 赋值运算符：同时锁住两个对象，避免死锁
    EnvDataCpp& operator=(const EnvDataCpp &other) {
        if (this != &other) {
            std::scoped_lock lock(mtx, other.mtx);  // C++17 多锁
            pm25 = other.pm25; pm10 = other.pm10;
            humidity = other.humidity; temperature = other.temperature;
            tvoc = other.tvoc; ch2o = other.ch2o;
            co2 = other.co2; o3 = other.o3;
        }
        return *this;
    }
};
```

**写入端（设备 cpp 文件）加锁：**

```cpp
// dev_humidifier.cpp - procEnvData
void DevHumidifier::procEnvData(const uint8_t *resp, size_t resp_len, int rc) {
    // ... 解析出 co2, ch2o, tvoc, pm25, pm10 ...

    // 先用局部变量保存解析结果
    int co2  = ParseService::extractU16(resp, 0);
    int ch2o = ParseService::extractU16(resp, 1);
    int tvoc = ParseService::extractU16(resp, 2);
    int pm25 = ParseService::extractU16(resp, 3);
    int pm10 = ParseService::extractU16(resp, 4);

    // 一次性加锁写入所有字段
    {
        std::lock_guard<std::mutex> lock(env_.mtx);
        env_.co2 = co2; env_.ch2o = ch2o;
        env_.tvoc = tvoc; env_.pm25 = pm25; env_.pm10 = pm10;
    }
}
```

**读取端通过拷贝构造获取快照：**

```cpp
// 通过 getEnvData() 返回拷贝，拷贝构造函数会自动加锁
EnvDataCpp data = dev_humidifier.getEnvData();
// 使用 data.pm25, data.co2 等，此时已不持有锁
```

## 4. 优化二：消除安防应用冗余轮询线程

### 4.1 问题分析

优化前，`AppSecurity` 有自己的 `pollingThread()`，每 2 秒执行一次：

```cpp
void AppSecurity::pollingThread() {
    while (m_running) {
        // 从全局设备读取数据
        int waterState = dev_water.getWaterState();
        int irState = dev_infrared.getInfraredState();
        int radarState = dev_infrared.getRadarState();

        // 复制到自己的 atomic 字段
        m_state.waterSensorState.store(waterState);
        m_state.infraredState.store(irState);
        m_state.radarState.store(radarState);

        // 计算风险等级
        evaluateRisk();
        std::this_thread::sleep_for(std::chrono::seconds(2));
    }
}
```

这存在以下问题：
1. **冗余数据复制**：`dev_water`、`dev_infrared` 已经在主轮询系统中持续更新，安防线程只是把同样的数据复制一份到 `m_state`
2. **数据延迟**：安防线程每 2 秒才更新一次，而主轮询系统的数据是实时的
3. **资源浪费**：额外的线程占用 CPU 和内存

### 4.2 解决方案

**核心思路：删除安防轮询线程，API 处理时直接从全局设备读取实时数据。**

**改造前的数据流：**

```
主轮询系统 ──写入──→ dev_water.water_state_
                         │
安防轮询线程 ──读取──→ 复制到 m_state.waterSensorState
                         │
Web API ──读取──→ m_state.waterSensorState
```

**改造后的数据流：**

```
主轮询系统 ──写入──→ dev_water.water_state_
                         │
Web API ──直接读取──→ dev_water.getWaterState()
```

**API 处理函数改造：**

```cpp
// 改造前：从 m_state 读取（2秒前的旧数据）
HttpResponse AppSecurity::handleGetStatus(const HttpRequest&) {
    int waterState = m_state.waterSensorState.load();   // ← 旧数据
    int irState = m_state.infraredState.load();
    // ...
}

// 改造后：直接从全局设备读取（实时数据）
HttpResponse AppSecurity::handleGetStatus(const HttpRequest&) {
    int waterState = dev_water.getWaterState();          // ← 实时数据
    int irState = dev_infrared.getInfraredState();
    int radarState = dev_infrared.getRadarState();
    float waterLevel = m_state.waterLevel.load();

    // 实时计算风险等级
    evaluateRisk(waterState, irState, radarState);
    // ... 组装 JSON ...
}
```

**evaluateRisk 改为接收参数：**

```cpp
// 改造前：读取 m_state 中的缓存值
void AppSecurity::evaluateRisk() {
    m_state.waterRisk = calcWaterRisk(m_state.waterLevel.load(),
                                       m_state.waterSensorState.load());
    // ...
}

// 改造后：接收实时参数
void AppSecurity::evaluateRisk(int waterState, int irState, int radarState) {
    m_state.waterRisk = calcWaterRisk(m_state.waterLevel.load(), waterState);
    m_state.intrusionRisk = calcIntrusionRisk(irState, radarState);
    m_state.gasRisk = calcGasRisk(m_state.gasConcentration.load());
    // ...
}
```

**SecurityState 结构简化：**

```cpp
// 改造前：包含冗余的设备状态缓存
struct SecurityState {
    std::atomic<int> waterSensorState{0};    // ← 删除，从 dev_water 实时读取
    std::atomic<int> infraredState{0};       // ← 删除，从 dev_infrared 实时读取
    std::atomic<int> radarState{0};          // ← 删除，从 dev_infrared 实时读取
    std::atomic<float> waterLevel{0.2f};
    // ... 其他字段 ...
};

// 改造后：只保留应用自身的状态
struct SecurityState {
    std::atomic<float> waterLevel{0.2f};     // 模拟值，用于无硬件演示
    SecurityRiskLevel waterRisk{SecurityRiskLevel::LOW};
    SecurityRiskLevel intrusionRisk{SecurityRiskLevel::LOW};
    std::atomic<int> gasConcentration{12};   // 模拟值
    SecurityRiskLevel gasRisk{SecurityRiskLevel::LOW};
    std::atomic<bool> alarmSoundActive{false};
    std::atomic<bool> alarmCenterActive{false};
    std::atomic<bool> ventilationActive{false};
    std::atomic<bool> waterControlActive{false};
    SecurityRiskLevel overallRisk{SecurityRiskLevel::LOW};
    std::atomic<bool> systemNormal{true};

```

## 5. 优化三：Web API 控制命令走 CommandQueue

### 5.1 问题分析

优化前，`/api/control` 处理器在 Web 服务器线程中直接调用设备控制方法：

```cpp
// web_server.cpp - 在 Web 线程上直接执行 Modbus 写操作
if (device == "ac" && g_modbus != nullptr) {
    if (action == "cool_on") rc = dev_ac.setCoolOn(*g_modbus, resp, &resp_len);
    // ...
}
```

这导致以下问题：

1. **串口竞争**：Web 线程直接调用 `ModbusService::writeReg()`，与轮询线程竞争 `SerialBus` 的 `recursive_mutex`。虽然不会数据损坏，但会阻塞 Web 线程等待串口释放
2. **阻塞 Web 响应**：一次 Modbus 写操作包含：获取锁 → 构建帧 → 发送 → 等待响应 → 解析，耗时可达数百毫秒。在此期间 HTTP 连接被占用
3. **无法优先级调度**：所有控制命令以相同优先级执行，无法区分紧急报警和普通控制

### 5.2 解决方案

**核心思路：Web 线程只负责提交命令到 CommandQueue，由命令处理线程异步执行 Modbus 写操作。**

**改造前的调用链：**

```
Web 线程 ──直接调用──→ dev_ac.setCoolOn(*g_modbus, ...)
                           │
                           └──→ ModbusService::writeReg()
                                    │
                                    └──→ SerialBus::lock()  ← 与轮询线程竞争
```

**改造后的调用链：**

```
Web 线程 ──提交──→ g_cmd_queue->writeRegister(DEV_AC_ADDR, REG_AC_COOL_ON, 1)
                       │
                       └──→ 返回命令 ID，Web 线程立即响应 {"status":"submitted"}
                                │
命令处理线程 ──异步执行──→ ModbusService::writeReg()
                              │
                              └──→ SerialBus::lock()  ← 有序调度，无竞争
```

**代码改造：**

```cpp
// 改造前：Web 线程直接执行 Modbus 写操作
if (device == "ac" && g_modbus != nullptr) {
    if (action == "cool_on") rc = dev_ac.setCoolOn(*g_modbus, resp, &resp_len);
    else if (action == "cool_off") rc = dev_ac.setCoolOff(*g_modbus, resp, &resp_len);
    // ...
}
const char* msg = (rc == 0) ? "{\"status\":\"success\"}" : "{\"status\":\"failed\"}";

// 改造后：通过 CommandQueue 异步提交
bool submitted = false;
if (g_cmd_queue != nullptr) {
    if (device == "ac") {
        if (action == "cool_on")
            submitted = g_cmd_queue->writeRegister(DEV_AC_ADDR, REG_AC_COOL_ON, 1) > 0;
        else if (action == "cool_off")
            submitted = g_cmd_queue->writeRegister(DEV_AC_ADDR, REG_AC_COOL_OFF, 1) > 0;
        // ...
    }
}
const char* msg = submitted ? "{\"status\":\"submitted\"}" : "{\"status\":\"failed\"}";
```

**CommandQueue 接口说明：**

```cpp

public:

    // @param regAddr   寄存器地址（如 REG_AC_COOL_ON = 0x0000）

                           CommandPriority priority = CommandPriority::NORMAL,
                           std::function<void(const CommandResult &)> callback = nullptr);

    // 提交写线圈命令（异步，立即返回）
    uint64_t writeCoil(uint8_t devAddr, uint16_t coilAddr, bool value,
                       CommandPriority priority = CommandPriority::NORMAL,
                       std::function<void(const CommandResult &)> callback = nullptr);
};
```

## 9. 优化五：信号处理与优雅退出

### 9.1 问题分析

系统在多线程环境下存在两个严重的退出问题：

**问题 1：Ctrl+C 无法终止程序**

主循环使用 `usleep()` 等待，在多线程程序中 SIGINT 可能被轮询线程接收而非主线程，导致 `usleep()` 不被中断。

**问题 2：`serialBus.close()` 死锁**

`SerialBus::transact()` 在整个事务期间（包括 I/O 阻塞）持有 `recursive_mutex`。`close()` 也需要获取同一 mutex，导致主线程等待所有轮询线程完成 I/O，耗时 30+ 秒。

时间线分析（优化前）：
```
08:40:46.272 - "正在关闭串口..." (开始)
08:41:15.793 - "正在停止轮询..." (29.5秒后才返回!)
```

### 9.2 解决方案

#### 9.2.1 Self-Pipe Trick 信号处理

```cpp
// 创建信号通知管道
static int g_signal_pipe[2] = {-1, -1};
pipe(g_signal_pipe);
fcntl(g_signal_pipe[0], F_SETFL, O_NONBLOCK);

// 信号处理函数: 设置退出标志 + 写管道唤醒 select()
static void signal_handler(int sig) {
    (void)sig;
    g_web_running = false;
    char c = 'X';
    write(g_signal_pipe[1], &c, 1);
}

// 主循环使用 select() 监听管道
while (g_web_running) {
    fd_set rfds;
    FD_ZERO(&rfds);
    FD_SET(g_signal_pipe[0], &rfds);
    struct timeval tv = {1, 0};  // 1秒超时
    select(g_signal_pipe[0] + 1, &rfds, NULL, NULL, &tv);
    if (FD_ISSET(g_signal_pipe[0], &rfds)) {
        char buf[16];
        while (read(g_signal_pipe[0], buf, sizeof(buf)) > 0) {}
    }
    if (!g_web_running) break;
    // ... 打印统计 ...
}
```

关键点：
- `sigaction` 不设置 `SA_RESTART`，确保 `select()` 被 EINTR 中断
- 1 秒超时确保 Ctrl+C 响应延迟 < 1 秒
- 管道读端设为非阻塞，防止 drain 时阻塞

#### 9.2.2 SerialBus Shutdown Pipe

在 `SerialBus` 中添加 shutdown pipe，用于唤醒阻塞在 `select()` 上的轮询线程：

```cpp
class SerialBus {
    int shutdown_pipe_[2] = {-1, -1};
    // ...
};
```

`rawRecv()` 的 `select()` 同时监听串口 fd 和 shutdown pipe：

```cpp
int SerialBus::rawRecv(...) {
    int fd = fd_;
    int pipe_fd = shutdown_pipe_[0];
    int nfds = (fd > pipe_fd ? fd : pipe_fd) + 1;

    while (...) {
        FD_ZERO(&readfds);
        FD_SET(fd, &readfds);
        if (pipe_fd >= 0) FD_SET(pipe_fd, &readfds);

        int sel = select(nfds, &readfds, NULL, NULL, &tv);
        // shutdown pipe 可读 → 正在关闭
        if (pipe_fd >= 0 && FD_ISSET(pipe_fd, &readfds)) {
            return -1;
        }
        // ... 正常读取 ...
    }
}
```

`close()` 写入 shutdown pipe 唤醒所有阻塞线程：

```cpp
void SerialBus::close() {
    // 写管道唤醒阻塞在 select() 上的线程
    if (shutdown_pipe_[1] >= 0) {
        char c = 'X';
        write(shutdown_pipe_[1], &c, 1);
    }
    std::lock_guard<std::recursive_mutex> lock(mtx_);
    if (fd_ >= 0) {
        ::close(fd_);
        fd_ = -1;
    }
}
```

#### 9.2.3 transact() 释放 I/O 锁

将 `transact()` 中的 mutex 保护范围缩小，不在 I/O 期间持锁：

```cpp
int SerialBus::transact(...) {
    int local_fd;
    {
        // 短暂持锁: 检查 fd、重连、记录争用
        std::unique_lock<std::recursive_mutex> lock(mtx_);
        // ... fd 检查和重连 ...
        local_fd = fd_;
    }  // 释放锁

    // I/O 不持锁
    usleep(inter_frame_delay_us_);
    tcflush(local_fd, TCIOFLUSH);
    rawSend(request, request_len);   // 内部用 local_fd
    rawRecv(response, ...);          // 内部用 local_fd

    // 错误处理时短暂持锁更新统计
    if (rc != 0) {
        std::lock_guard<std::recursive_mutex> lock(mtx_);
        stats_.totalErrors++;
    }
}
```

### 9.4 退出流程

```
Ctrl+C
  → signal_handler: g_web_running=false, 写 signal_pipe
  → 主循环 select() 返回, 检测到 g_web_running=false
  → pthread_join(web_tid)          // Web 服务器退出 (~1s)
  → appMgr.stopAll()               // 安防应用停止
  → cmdQueue.stop()                // 命令队列停止
  → serialBus.close()              // 写 shutdown_pipe 唤醒轮询线程, 关闭串口 fd
  → poller.stop()                  // 所有轮询线程立即退出 (~20ms)
  → 打印最终统计
  → return 0
```

优化后退出时间：**~2 秒**（主要是 Web 服务器 accept 超时），相比优化前的 **30+ 秒**。

## 10. 优化六：EnvDataCpp 死锁修复

### 10.1 问题分析

`DevHumidifier::init()` 和 `DevAirPurifier::init()` 中，先用 `lock_guard` 锁定 `env_.mtx`，再调用 `env_ = EnvDataCpp{}`。赋值运算符内部使用 `scoped_lock(mtx, other.mtx)`，由于 `std::mutex` 不可重入，同一线程二次加锁导致死锁。

```cpp
// 死锁代码
void DevHumidifier::init() {
    std::lock_guard<std::mutex> lock(env_.mtx);  // 第一次加锁
    env_ = EnvDataCpp{};  // 赋值运算符内部 scoped_lock → 第二次加锁 → 死锁!
}
```

### 10.2 解决方案

移除外层 `lock_guard`，直接赋值。赋值运算符内部的 `scoped_lock` 已经足够保护：

```cpp
void DevHumidifier::init() {
    status_.reset();
    env_ = EnvDataCpp{};  // 赋值运算符内部有 scoped_lock 保护
    power_state_.store(0);
    fault_state_.store(0);
}
```

### 10.3 修改文件

- `devices/dev_humidifier.cpp` — 移除 `init()` 中的外层 lock_guard
- `devices/dev_air_purifier.cpp` — 同上
